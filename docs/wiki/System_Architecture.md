# 기술적 의사결정

## 1. 도입 배경

본 프로젝트에서 배치 서비스를 도입한 가장 큰 이유는 약 15만 건의 도서 초기 데이터를 안정적으로 적재하기 위함이었습니다. 대량의 외부 데이터를 수집하고 가공하는 과정에서 발생할 수 있는 메모리 부족 문제와 작업 실패 시의 재처리 문제를 해결하기 위해 Spring Batch를 학습하여 적용했습니다.

초기 데이터 적재를 성공적으로 마친 후, API 서버(Bookstore Service)의 부하를 줄이기 위해 기존에 서버 내부에서 처리하던 무거운 백그라운드 작업들을 배치 서비스로 하나씩 이관하기 시작했습니다.

## 2. 배치 서비스의 주요 역할

현재 배치 서비스는 크게 세 가지 핵심 작업을 담당하고 있습니다.

### 2.1. 도서 데이터 초기 적재 및 인덱싱
* 알라딘 API와 연동하여 15만 건의 도서 정보를 수집하고, 이를 MySQL과 Elasticsearch에 일괄 적재합니다.
* 초기 적재 이후에는 신규 도서 등록이나 정보 갱신 발생 시 검색 엔진에 반영하는 역할을 수행합니다.

### 2.2. 고아 이미지 자원 정리
* 에디터 작업 중 사용자가 이미지만 업로드하고 글 저장을 포기한 경우, 스토리지(MinIO)에는 참조되지 않는 파일이 남게 됩니다.
* 이를 실시간으로 감지하기 어렵기 때문에, 주기적으로 DB를 전수 조사하여 참조가 끊긴 지 24시간이 지난 파일들을 삭제합니다.

### 2.3. 도서 할인가 재계산
* 할인 정책이 변경될 경우 수만 권의 도서 가격을 다시 계산해야 합니다.
* 이 작업은 API 서버에서 수행하기에 트랜잭션이 너무 길고 무거워질 수 있으므로, 메시지 큐(RabbitMQ)를 통해 이벤트를 전달받아 배치 서버에서 비동기로 처리합니다.

## 3. 프레임워크 및 기술 선택 이유

### 3.1. Spring Batch를 선택한 이유
* 자원 효율성: 청크(Chunk) 단위 처리를 통해 대량의 데이터를 안정적으로 다룰 수 있습니다.
* 재시작 가능성: 작업이 중간에 실패하더라도 메타 테이블 기록을 바탕으로 중단된 지점부터 다시 시작할 수 있어 운영 부담이 적습니다.

### 3.2. JDBC 배치 업데이트(Bulk Insert) 사용 이유
* JPA의 saveAll 방식은 MySQL의 IDENTITY 전략 사용 시 건건이 Insert 쿼리가 발생하여 대량 적재에 부적합했습니다.
* 성능 확보를 위해 JdbcTemplate을 사용하여 수천 건의 데이터를 단일 패킷으로 묶어 전송하는 방식을 택했습니다.

### 3.3. RabbitMQ 도입 이유
* 서비스 간 결합도 제거: API 서버가 배치 서버의 상태를 알 필요 없이 작업 요청(이벤트)만 던지고 즉시 응답할 수 있게 분리했습니다.
* 작업 유실 방지: 배치 서버가 일시적으로 중단되더라도 메시지 큐에 요청이 보존되어 나중에 안전하게 처리할 수 있습니다.

## 4. 한계점 및 향후 과제

현재 API 서버(Bookstore Service) 내부에는 여전히 등급 산정이나 포인트 만료 처리와 같은 스케줄러 로직들이 남아있습니다. 프로젝트 마감 기한 내에 관리자 기능과 핵심 API 구현을 우선시했기 때문에, 모든 백그라운드 로직을 배치로 이관하지는 못했습니다.

현재는 부하가 가장 큰 '도서 가격 재계산'부터 우선적으로 분리한 상태이며, 향후 운영 안정성을 위해 나머지 스케줄러 작업들도 배치 서비스로 통합하여 API 서버의 역할을 사용자 요청 대응으로만 한정시키는 리팩토링이 필요합니다.
